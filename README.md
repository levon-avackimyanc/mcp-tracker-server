# Когда пользователь — не человек: тестирование MCP-серверов

Демо-стенд к докладу и eval-харнесс к нему.

MCP-сервер «трекер задач» опубликован в четырёх версиях контракта. Доменная логика
у них общая, отличаются только описания тулов, схемы параметров и тексты ошибок:

- **v1** — технически исправный сервер с описаниями «как javadoc»: `query_items` —
  «Queries items using filter». Тесты зелёные, агент со сценарием не справляется:
  тул он выбирает верно, но не угадывает формат фильтра, получает пустой список
  и отвечает пользователю, что задач нет.
- **v1b** — тот же v1, в котором переписано **одно описание**: у `query_items` появился
  формат фильтра, перечень статусов и пример. Код поиска не тронут — он с самого начала
  находил нужные задачи. Дифф снимков `tools-v1.json` → `tools-v1b.json` состоит
  из одной строки; сценарий проходит.
- **v1err** — описания v1, тексты ошибок v2. Изолирует вклад одного слоя контракта:
  видно, помогает ли агенту хорошая ошибка, когда описания остались плохими.
- **v2** — тот же код, переписан только контракт: описание отвечает на вопрос
  «когда вызывать тул», у параметров формат и пример, статусы перечислением, ошибки
  содержат подсказку для самостоятельного исправления вызова.

Тезис доклада: описание тула — функциональная часть контракта, и её можно и нужно
ставить под тест.

## Структура

```
server-java/   MCP-сервер на Spring Boot: четыре профиля контракта и тесты
eval/          прогон сценариев агентом, success rate и число вызовов до успеха
.mcp.json      регистрация сервера в Claude Code
```

У каждой директории свой README с подробностями.

## Быстрый старт

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)   # macOS; на Linux — путь к JDK 21
cd server-java && ./mvnw package && cd ..

python3 server-java/scripts/mcp-stdio.py v2 tools/list   # контракт глазами агента
python3 eval/harness.py -n 3                             # черновой прогон сценариев
```

Агентом в демонстрациях выступает Claude Code: сервер подключается локально через
`.mcp.json`, внешние ключи доступа не нужны. Запускать `claude` нужно из корня
репозитория — путь к jar в конфигурации относительный.

## Что здесь тестируется

1. **Юнит-тесты** (`TaskStoreTest`) — логика трекера, быстро и детерминированно.
2. **Поведение тулов** (`ToolBehaviourTest`) — что именно получает агент в ответе,
   включая тексты ошибок.
3. **Снимок контракта** (`ToolsListSnapshotTest`) — полный `tools/list` в системе
   контроля версий: любая правка описания или схемы роняет сборку и попадает
   в code review отдельным диффом. Там же проверяется инвариант демонстрации:
   контракты v1 и v1b расходятся ровно в одной строке с описанием.
4. **Прогон сценариев агентом** (`eval/harness.py`) — задача на естественном языке,
   проверка итогового результата, повтор N раз, success rate и число вызовов
   до успеха. Единственный уровень, на котором видна разница между версиями контракта.

Первые три уровня одинаково зелены на всех четырёх профилях: работоспособность кода
не зависит от качества описаний. Что именно ломается в v1, показывает только
четвёртый — [результаты прогонов и разбор](eval/README.md#результаты).
