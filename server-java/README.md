# tracker-mcp

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](../LICENSE)

MCP-сервер трекера задач на Spring Boot — демо-стенд к докладу
«Когда пользователь — не человек: тестирование MCP-серверов».

Одна и та же доменная логика публикуется в нескольких версиях контракта. Версии
отличаются **только текстами описаний, схемами параметров и сообщениями об ошибках**;
доменный код (`domain/TaskStore`) общий. Поэтому провал сценария на одной из версий
нельзя списать на баг в логике — стенд изолирует вклад контракта.

Тезис доклада: описание тула — функциональная часть контракта, и её можно и нужно
ставить под тест.

## Версии контракта

Версия выбирается профилем Spring.

| Профиль | Тулы | Описания | Ошибки |
|---------|------|----------|--------|
| `v1` | `query_items`, `create_item`, `get_report` | «как javadoc»: одна строка, параметры без описаний | `Error: Invalid date` |
| `v1b` | те же, что в `v1` | как в `v1`, но у `query_items` переписано **одно** описание: формат фильтра, статусы, пример | как в `v1` |
| `v1err` | те же, что в `v1` | как в `v1` | как в `v2`: формат, пример, текущая дата |
| `v2` | `search_tasks`, `create_task`, `update_task`, `get_task_report` | когда вызывать тул, форматы и примеры параметров, статусы перечислением | формат + пример + текущая дата |

- **v1** — технически исправный сервер: тесты зелёные, но агент со сценарием не справляется.
  Тул он выбирает верно, не угадывает формат фильтра, получает пустой список и отвечает
  пользователю, что задач нет.
- **v1b** — правка одного описания. Код поиска не тронут: он с самого начала находил нужные
  задачи. Дифф снимков `tools-v1.json` → `tools-v1b.json` состоит из одной строки, и сценарий
  проходит.
- **v1err** — улучшены только сообщения об ошибках. Профиль показывает, помогает ли агенту
  выбраться хороший текст ошибки, когда описания остались плохими. В `tools/list` тексты ошибок
  не попадают — snapshot-тест их не страхует, видно их только в прогоне сценария.
- **v2** — переписан контракт целиком.

## Стек

Java 21, Spring Boot 4.1.0, Spring AI 2.0.0 (`spring-ai-starter-mcp-server`), транспорт stdio.

## Сборка и тесты

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)   # macOS; на Linux — путь к JDK 21
./mvnw test        # юнит-тесты, тесты поведения и снимки контракта
./mvnw package     # target/tracker-mcp.jar
```

Сборка требует **Java 21**: Maven по умолчанию может использовать более новый JDK,
поэтому `JAVA_HOME` задаётся явно. Отчёт покрытия JaCoCo — `target/site/jacoco/index.html`.

## Запуск

```bash
java -jar target/tracker-mcp.jar --spring.profiles.active=v1
```

Сервер общается по stdio, поэтому stdout занят протоколом: баннер отключён, логи пишутся
в `logs/tracker-mcp.log`. Любая посторонняя строка в stdout разрывает сессию.

## Подключение к Claude Code

`.mcp.json` в корне репозитория регистрирует сервер под именем `tracker`. Запускать
`claude` нужно из корня репозитория (на уровень выше этой директории) — путь к jar
в конфигурации относительный.
Переключение версии — правка одного значения `--spring.profiles.active` и перезапуск сессии.

Состояние трекера живёт в памяти процесса: перезапуск возвращает исходные восемь задач.

## Просмотр контракта и вызовы вручную

Из этой директории:

```bash
python3 scripts/mcp-stdio.py v2 tools/list
python3 scripts/mcp-stdio.py v1 tools/call query_items '{"filter": "просроченные задачи Алексея"}'
python3 scripts/mcp-stdio.py v2 tools/call create_task '{"title": "Отчёт", "due_date": "завтра"}'
```

Скрипт поднимает сервер, выполняет один запрос и печатает ответ — то же самое, что получит
агент. Полноценный хост для этого не нужен.

## Тесты

- `TaskStoreTest` — юнит-тесты доменной логики.
- `ToolBehaviourTest` — поведение тулов на уровне ответа: что именно получает агент,
  включая тексты ошибок разных версий.
- `ToolsListSnapshotTest` — снимок контракта `tools/list` в `src/test/resources/snapshots/`.
  В снимок попадают имя тула, описание и схема параметров — то, на основании чего модель
  принимает решение о вызове. Правка описания роняет тест; осознанное изменение фиксируется
  командой `./mvnw test -Dsnapshot.update=true`, и эталон уходит в code review отдельным
  диффом. Там же проверяется инвариант демонстрации: контракты `v1` и `v1b` расходятся ровно
  в одной строке с описанием.

Все тесты на всех версиях проходят одинаково успешно — работоспособность кода не зависит от
качества описаний. Что именно ломается в `v1`, показывает только прогон сценария агентом:
задача на естественном языке, проверка итогового результата, повтор N раз, метрика
success rate и число вызовов до успеха.

## Структура

```
src/main/java/ru/mcprnd/tracker/
  domain/          логика трекера, общая для всех версий контракта
  tools/v1/        контракт v1
  tools/v1b/       контракт v1 с одним переписанным описанием
  tools/v1err/     контракт v1 с хорошими сообщениями об ошибках
  tools/v2/        контракт v2
src/test/resources/snapshots/   эталоны tools/list
scripts/mcp-stdio.py            минимальный stdio-клиент MCP
```

Прогон сценариев агентом против этих профилей — в [`../eval`](../eval/README.md).
