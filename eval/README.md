# eval — прогон сценариев агентом

Четвёртый уровень тестирования стенда: задача формулируется на естественном языке,
её решает живой агент против сервера в заданном профиле контракта, результат
проверяется автоматически, прогон повторяется N раз. Это единственный уровень,
на котором видна разница между версиями контракта: юнит-тесты, тесты поведения
и снимок `tools/list` одинаково зелены на всех четырёх профилях.

## Как устроено

Агентом выступает Claude Code в headless-режиме. На каждый прогон запускается
отдельный процесс:

```
claude -p "<задача>" --mcp-config <профиль>.json --strict-mcp-config \
       --setting-sources "" --tools ToolSearch \
       --allowedTools "mcp__tracker__*" --model <модель> \
       --output-format stream-json --verbose
```

Отсюда два свойства:

- **API-ключ не нужен** — используется уже настроенная аутентификация Claude Code;
- **каждый прогон независим** — чистый контекст, агент не может подсмотреть рабочий
  формат фильтра в предыдущей попытке.

Ключи `--setting-sources ""` и `--tools ToolSearch` изолируют измерение: без первого
плагины из пользовательских настроек добавляют десятки тулов, хост переходит на
отложенную загрузку схем, и слабая модель спотыкается об неё, а не об наш контракт;
без второго агент считает даты через Bash и порождает сабагентов, и это попадает
в метрику вызовов.

Конфиг MCP под каждый профиль генерируется во временный каталог, в репозитории
не хранится.

## Запуск

```bash
cd server-java && ./mvnw package && cd ..   # харнесс запускает собранный jar
python3 eval/harness.py                     # 4 профиля × 3 сценария × 10, модель sonnet
python3 eval/harness.py -n 3 --model haiku  # черновой прогон
python3 eval/harness.py --profiles v1 v1b   # только две версии
```

Зависимостей нет — нужны Python 3 и `claude` в `PATH`. Полный прогон (120 запусков)
занимает около 15 минут; стоимость печатается в конце отчёта.

## Сценарии

| id | Задача | Проверка успеха |
|----|--------|-----------------|
| `overdue-alexey` | «Найди все просроченные задачи Алексея, ответь только списком id» | в ответе ровно `T-1`, `T-2`, `T-3`; `T-4` (задача Алексея, но не просроченная) и `T-5` (просроченная, но чужая) отсутствуют |
| `create-date` | «Создай задачу со сроком 5 августа 2026 к 18:00» | среди вызовов есть успешный `create_*` с `due_date: 2026-08-05` |
| `tasks-per-person` | «Сколько задач у каждого исполнителя?» | названы верные числа: Алексей 4, Мария 2, Иван 2 |

Формулировки одинаковы для всех профилей — меняется только контракт сервера.
Требование к формату ответа («списком id», «строками вида Имя: число») намеренно
жёсткое: иначе проверка превращается в разбор свободного текста и сама начинает
ошибаться.

Каждый сценарий бьёт в свою точку отказа:

- `overdue-alexey` — **не так вызвал**: тул выбран верно, но формат фильтра не угадан.
  Пустой результат приходит не ошибкой, а молчаливым `[]`, поэтому хороший текст
  ошибки здесь не помогает — лечит только описание.
- `create-date` — **самоисправление по ошибке**: срок задан со временем суток, деть
  его некуда, агент получает отказ, и дальше всё решает текст ошибки.
- `tasks-per-person` — **различимость похожих тулов**: ответ целиком лежит
  в `get_report`, но его можно набрать и перебором поиска по каждому имени.

## Метрики

Кроме **success rate** харнесс считает **среднее число вызовов до успеха**. Вторая
метрика нужна потому, что на сильной модели плохой контракт часто не роняет сценарий,
а дорожает: агент добирается до ответа перебором форматов. Бинарный pass/fail такую
деградацию не видит.

Прогон, в котором агент не запустился (таймаут, недоступна модель, ненулевой код
возврата), помечается `broken` и в метрику не входит: он ничего не говорит о контракте,
а засчитанный как FAIL — портит картину.

## Результаты

`results/report-sonnet.txt` и `results/report-haiku.txt` — вывод полного прогона
(4 профиля × 3 сценария × 10). Рядом лежат сырые данные этих двух прогонов в `.jsonl`:
по строке на прогон — вызовы тулов с аргументами и ответами, финальный ответ агента,
стоимость, вердикт проверки.

Sonnet:

```
сценарий              v1   v1err     v1b      v2
overdue-alexey      3/10    3/10   10/10   10/10
  вызовов            2.7     2.3     1.0     1.0
create-date        10/10   10/10   10/10   10/10
  вызовов            3.4     2.0     3.4     1.0
tasks-per-person   10/10   10/10   10/10   10/10
  вызовов            3.2     3.2     4.6     1.0
ИТОГО                77%     77%    100%    100%
```

Haiku:

```
сценарий              v1   v1err     v1b      v2
overdue-alexey      8/10    9/10   10/10   10/10
  вызовов            5.2     6.6     1.0     1.0
create-date        10/10   10/10   10/10   10/10
  вызовов            2.2     2.0     2.7     1.0
tasks-per-person    9/10   10/10   10/10   10/10
  вызовов            2.4     2.5     1.8     1.0
ИТОГО                90%     97%    100%    100%
```

Что из этого следует:

- **Правка одного описания меняет метрику**: `v1` → `v1b` на `overdue-alexey`
  даёт 3/10 → 10/10 на Sonnet. Код поиска не тронут.
- **Более сильная модель хуже на плохом контракте.** Sonnet сдаётся через ~2.7 вызова
  и сообщает пользователю, что задач нет; Haiku перебирает форматы (5.2 вызова)
  и доходит до ответа. Success rate зависит и от модели, которую выбирает хост, —
  автор сервера её не контролирует.
- **Хороший текст ошибки помогает не везде.** На `create-date` он срезает перебор
  (`v1` 3.4 → `v1err` 2.0 вызова), на `overdue-alexey` не даёт ничего: пустой
  результат поиска — не ошибка.
- **Улучшение может дать регрессию.** Правка `v1` → `v1b` подняла `overdue-alexey`
  до 10/10 и одновременно испортила `tasks-per-person` (3.2 → 4.6 вызова): агент
  поверил улучшенному поиску и перестал доходить до `get_report`. Дифф снимка
  контракта показал бы только плюс.

Прогоны воспроизводимы, но не детерминированы: точные числа от запуска к запуску
отличаются, качественная картина устойчива.
